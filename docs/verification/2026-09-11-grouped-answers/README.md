# 题组选择与整组提交验证 · 2026-09-11

用户在 `aidlc-demo-full / 260909-precision` 能看到四道题，却无法选择。题单来自已保存的
`requirements-analysis-questions.md`，没有原生问题控件；旧实现因此禁用全部选项，
同时将 `select all that apply` 误判为单选。

修复后，格式受支持、读取稳定的题单可直接提供单选、多选和 Other 输入。题号、选项、
顺序和原文均来自文件。未完成的题必须一次答完；确认面板显示实际发送内容。
题单格式含歧义、题单在确认期间发生变化、会话忙碌或原生问题仍在等待时，提交会被拒绝。
原生问题控件继续通过原会话处理，本次不声称实现了原生控件的回答接口。

## 真实投递

验证环境为 KiroCrew `0.6.0-insider.6`、AI-DLC `2.7.1`，使用独立临时仓库。
代理实际生成两组选项相同的四题，覆盖中文单选、英文单选、多选及含标点的多行 Other。

第一轮发现：题号与文件答案对应正确，但逐题调用 `aidlc-log.ts answer` 会消耗同一条
HUMAN_TURN，第二次调用被拒绝。单纯开启控件无法保证审计完整，因此没有直接发布。

第二轮采用 `wire-text.json` v2：`Q<n>` 答案后附明确的整组记录说明，要求全部答案进入
**同一条**回答回执。实测结果见 [投递证据](native-proof.json)：

- 主机会话只收到一次完整题组消息。
- 四个 `[Answer]` 均对应正确，多选保留 A、C，多行 Other 的第二行完整保留。
- 一条 `QUESTION_ANSWERED` 包含全部四题，未产生 `ERROR_LOGGED`。
- 流程停在未回答的 Consolidated Summary Confirmation，没有代为批准。

审计 Details 由引擎记录为摘要；确认面板、主机用户消息和题单是核对发送原文与答案全文的依据。
读取器同时修复了普通段落形式的多行答案只显示首行的问题。

## 浏览器实测补充：错误判定时机

第一次从完整页面提交时，主机只收到一次消息，四题也正确落盘，但代理的命令用法探查
产生三条错误，Studio 在回合尚未结束时提前标为 Failed。该证据促成第 21 项修复：
保留运行中的操作与租约，回合结束后先检查成功证据，再分类仍未恢复的错误。
这次失败验证作为历史证据保留，不计入最终成功验收。

最终验收使用一个新的隔离题组，重新执行完整的页面选择、确认、一次发送和状态结算。


最终 UI 操作只发送一次，确认面板与主机消息完全一致，四个文件答案完整，最终状态为
`ResolvedNoTransition`。代理探查命令产生两条临时错误，最终成功证据被正确采纳。
该 UI 专用冷会话通过测试代码预置题单，最后在会话中给出了汇总确认，但没有写入独立的
summary section；它验证页面投递与状态结算，不作为完整阶段编排的单独证明。
正式启动过的 v2 实测已验证汇总检查点落盘，两类证据分开保留。没有发送任何汇总批准。
